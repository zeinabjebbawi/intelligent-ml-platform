1 — The Big Picture: Four Pieces, One System

IntelliML is not one program. It is four separate programs that talk to each other over HTTP. Each one only knows how to do its own job, and none of them knows how the others are built internally — they only know each other's addresses and what JSON to send.

┌─────────────┐ ┌──────────────┐ ┌──────────────┐ │ React │ HTTP │ Django │ HTTP │ FastAPI │ │ (port 5173) │◄──────►│ (port 8080) │◄──────►│ (port 8001) │ │ frontend │ │ app server │ │ ML engine │ └─────────────┘ └──────┬───────┘ └──────┬───────┘ │ │ ▼ ▼ ┌─────────────┐ ┌──────────────┐ │ PostgreSQL │ │ ml-core │ │ database │ │ (plain .py │ └─────────────┘ │ functions) │ └──────────────┘
PieceTechnologyJob
ReactVite + React 19Everything the user sees and clicks. Never talks to the database directly — only to Django and FastAPI.
DjangoDjango 6 + DRF + SimpleJWTAccounts, login, projects, file upload, and the PostgreSQL database. The "business layer."
FastAPIFastAPI + UvicornAll machine learning computation. Never touches PostgreSQL directly.
ml-corePlain Python + pandas/scikit-learnNot a server — a folder of importable functions (cleaning.py, models.py, evaluation.py, pipelines.py). Only FastAPI imports it.
Why split it this way?
Django is the building manager — it handles accounts, stores files, keeps records, controls who gets in. FastAPI is the specialized lab technician down the hall — it only does scientific computation, and it does it fast because it never has to think about logins or file storage. The lab technician doesn't keep patient records; the building manager doesn't run lab tests. Each does one job well, and they hand work to each other. This is what "separation of concerns" means — not one giant tangled program, but boxes with narrow, well-defined openings between them.

Why does this matter practically? Because ml-core depends on heavy packages (numpy, pandas, scikit-learn, scipy) that Django's world has no reason to carry. Keeping ML code physically separate from Django means Django stays small and fast for what it does (auth, database, files), and the ML engine can be scaled, restarted, or even replaced independently without touching a single line of login code.

2 — How the Two Backends Connect (Django ↔ FastAPI)

Django and FastAPI are two completely separate processes, each with its own virtual environment (venv), listening on different ports (8080 and 8001). They do not share memory, they do not import each other's code, and they do not know the other one exists except by network address. The only way they communicate is by sending each other plain HTTP requests — exactly like a browser would.

Concretely: when a user uploads a CSV, Django's DatasetUploadView (in backend-django/datasets/views.py) saves the file to disk, creates a Dataset row in PostgreSQL, and then — using Python's requests library, the same one you'd use to call any external API — sends a POST request to http://localhost:8001/ml/profile with the file's path. FastAPI receives that request, loads the CSV using ml-core's load_data() and profile_dataset(), and sends back a JSON response full of statistics. Django reads that response and saves it into the same Dataset row.

django --POST /ml/profile--> fastapi {file_path: "..."} django <--200 OK {profiling_result, health_score}-- fastapi
The most important defensive pattern in this project
That call is wrapped in a try/except. If FastAPI is not running, Django does not crash — the upload still succeeds, the dataset is saved with status='uploaded' instead of 'profiled', and the response tells the user to start the FastAPI server. One service being down never brings the other one down. This is the single most important resilience pattern in the whole backend — remember it, because you will reuse the exact same shape (try / except ConnectionError / except Exception) everywhere Django calls FastAPI in the future.

Why two separate venvs instead of one? A venv (virtual environment) is an isolated folder of installed Python packages, so one project's dependencies don't collide with another's. Django's venv (backend-django/.venv) has Django, DRF, psycopg2, and — because Django's own upload view needs it to call FastAPI — the requests library. FastAPI's venv (backend-fastapi/.venv) has FastAPI, Uvicorn, and the entire ML stack (numpy, pandas, scikit-learn, scipy) that ml-core needs. Neither venv needs the other's packages, so keeping them separate keeps each install lean and keeps a dependency conflict in one from ever breaking the other.

How FastAPI finds ml-core

ml-core is not installed as a normal package — it's a plain folder of .py files sitting at the project root, next to (not inside) backend-fastapi. For main.py to write from cleaning import load_data, Python has to be told where to look. The top of main.py does exactly that:

ML_CORE_PATH = os.path.join( os.path.dirname(os.path.dirname(os.path.abspath(__file__))), 'ml-core' ) sys.path.insert(0, ML_CORE_PATH)

In plain words: "take this file's own folder (backend-fastapi), go up one level to the project root, then look inside ml-core." That folder is added to Python's search path, so every from cleaning import ... / from models import ... / etc. in main.py now resolves correctly. There is also a setup.py in ml-core/ that lets you run pip install -e . from inside it (with the FastAPI venv active) to make the same four modules importable from anywhere — both mechanisms are in place, and either one alone is enough.

3 — How the Frontend Connects to Both Backends

React never touches ml-core or PostgreSQL. It only ever makes HTTP requests — to Django for anything about accounts/projects/files, and to FastAPI for anything about ML computation. All of that is centralized in one file: frontend/src/api.js.

export const djangoAPI = axios.create({ baseURL: 'http://localhost:8080' }) export const mlAPI = axios.create({ baseURL: 'http://localhost:8001' })

Two separate axios instances, one per backend. Every component imports pre-built functions from this file (authAPI.login(...), mlOpsAPI.profile(...)) instead of writing raw axios.post(url, ...) calls scattered across the codebase. This means if a URL or a required field ever changes, it's fixed in exactly one place.

The JWT interceptor

djangoAPI has an interceptor — a function that runs automatically before every single outgoing request — that reads the access token from localStorage and attaches it as an Authorization: Bearer <token> header:

djangoAPI.interceptors.request.use((config) => { const token = localStorage.getItem('access_token') if (token) config.headers.Authorization = `Bearer ${token}` return config })

This is why, after calling authAPI.login(...) once and saving the returned token to localStorage, every later call through djangoAPI (creating a project, uploading a file) is automatically authenticated — no component ever manually attaches the header itself. mlAPI deliberately has no such interceptor, because FastAPI's endpoints in this project do not require a login token — only Django's do.

4 — The Database: Apps, Models, Migrations

The database is PostgreSQL, and Django is the only piece of the system allowed to talk to it directly. FastAPI never opens a database connection — it only ever receives data (a file path) and returns data (a JSON dict). This is deliberate: it keeps a single source of truth for "who can write to the database," which makes debugging vastly simpler.

The four Django apps
AppModelsResponsibility
accountsUserProfileExtends Django's built-in User with experience level (beginner/expert) and onboarding status.
projectsProject, WorkflowStateA workspace per analysis. WorkflowState tracks which step of the journey map the user is on.
datasetsDataset, DatasetVersionAn uploaded CSV and every processed version of it (original → cleaned → encoded → normalized).
experimentsExperiment, AgentDecision, InsightCard, WhatIfSimulation, ReportOne training run, every decision the agent made, every generated insight, every saved simulation, every report.

Why UUIDs instead of auto-incrementing numbers for primary keys? Because /api/projects/1/ invites someone to simply try /api/projects/2/. A UUID like /api/projects/3a7b9c1d-.../ is unguessable — you cannot enumerate other people's data by changing a number in the URL.

Why JSONField for things like profiling_result, metrics, and step_data? Because their shape genuinely varies — a classification experiment's metrics dict has accuracy/f1_score; a regression one has rmse/r2; a clustering one has silhouette_score. Modeling every possible field as its own database column would mean dozens of always-empty columns and a new migration every time a new metric is added. PostgreSQL stores JSONField as JSONB — indexed and queryable — so this flexibility costs nothing in practice.

Migrations — what they actually are

Writing a model class in models.py changes nothing about the real database by itself — it's just Python. A migration is a generated file that describes the exact SQL needed to make the real database match your models. Two commands, always in this order:

python manage.py makemigrations # reads models.py, writes a migration file (a "recipe") python manage.py migrate # actually runs that recipe against PostgreSQL
The rule you must never break
Every time you add, remove, or change a field on any model, you must run makemigrations then migrate again. Skip this and your Python code and your real database silently disagree about what columns exist — the app will crash the moment it touches that model, usually with a confusing ProgrammingError: column does not exist.
5 — Authentication and JWT, Explained Fully

JWT stands for JSON Web Token. It is how Django knows who is making a request without asking for a password on every single click.

Step 1 — Register

POST /api/auth/register/ with an email and password. Django hashes the password (it is never stored in plain text — User.objects.create_user() does this automatically) and creates a User row. The post_save signal in accounts/models.py then automatically creates a matching UserProfile row.

Step 2 — Login

POST /api/auth/login/ with the same email/password. SimpleJWT checks the password against the stored hash and, if correct, returns two tokens: an access token and a refresh token.

Step 3 — Using the access token

Every future request to a protected endpoint (like creating a project) must include Authorization: Bearer <access_token>. DRF's JWTAuthentication decodes the token, verifies its signature (proving it really came from this server and wasn't tampered with), and sets request.user to the matching user — all before your view function even runs.

Step 4 — Expiry and refresh

In this project's SIMPLE_JWT settings: the access token lasts 24 hours, the refresh token lasts 7 days. Once the access token expires, the frontend sends the refresh token to POST /api/auth/token/refresh/ to get a new access token — without asking the user to log in again. ROTATE_REFRESH_TOKENS: True means every refresh also issues a brand-new refresh token, which is a security best practice (an old, possibly-stolen refresh token stops working once a new one is issued).

Simple analogy
A JWT is like a wristband at a festival. Security (login) checks your ID once at the gate and puts on the wristband. For the rest of the day, every stage's bouncer just glances at the wristband — they don't re-check your ID every time. The wristband has an expiry printed on it (24 hours here); once it's expired, you need a new one (the refresh step), but you don't need to show your ID card again, just your ticket stub (the refresh token).

Note: in this codebase, Django's username field is set to the user's email during registration (User.objects.create_user(username=email, ...)) — this is why the login request body uses the key username even though what you actually type in is an email address.

6 — CORS: What It Is, and Exactly What's Configured

CORS (Cross-Origin Resource Sharing) is a browser security rule, not a server rule. By default, a browser refuses to let JavaScript running on one origin (say, http://localhost:5173) read the response from a request to a different origin (http://localhost:8080) — even though the two are both "localhost," a different port counts as a different origin. Without any configuration, React's calls to Django and FastAPI would be silently blocked by the browser, even if the server responded successfully.

The server fixes this by explicitly telling the browser, via response headers, "requests from this specific origin are allowed." Both backends do this, but with different tools:

BackendToolConfigured origins
Djangodjango-cors-headers (CorsMiddleware)http://localhost:5173, http://localhost:3000
FastAPIStarlette's built-in CORSMiddlewarehttp://localhost:5173, http://localhost:3000, http://localhost:8080
A gap that existed until this pass, now fixed
corsheaders was added to Django's INSTALLED_APPS early on, but the middleware itself was never wired into MIDDLEWARE, and CORS_ALLOWED_ORIGINS was never set. That meant Django was silently rejecting cross-origin requests from React this whole time — it just never surfaced because nothing was calling Django from a browser yet. This is now fixed in core/settings.py: CorsMiddleware sits right after SecurityMiddleware (it must run early, before other middleware can reject the request), and the two dev origins are explicitly allowlisted.

One more detail worth knowing: for any "unsafe" request (POST, PUT, DELETE, or a GET with custom headers like Authorization), the browser first sends an invisible preflight request using the OPTIONS method, asking "am I allowed to make this real request?" before it sends the real one. That's what CorsMiddleware/CORSMiddleware are answering. You will never write this OPTIONS request yourself — the browser does it automatically, and you'll only ever notice it exists by seeing it appear in your browser's Network tab.

7 — The Complete Pipeline: CSV Upload to Final Result

This traces one dataset through the entire system, file by file, function by function.

1. Upload

React calls datasetsAPI.upload(projectId, formData) → POST /api/projects/<id>/datasets/upload/ on Django.

DatasetUploadView (in backend-django/datasets/views.py) verifies the project belongs to the logged-in user, saves the file to media/datasets/user_<id>/project_<id>/original.csv, reads it with pandas for a quick preview, and creates a Dataset row (status 'uploaded') plus a DatasetVersion row (version 1, type 'original').

2. The Django → FastAPI bridge fires

Still inside the same request, Django POSTs the saved file path to FastAPI's /ml/profile. FastAPI calls load_data() then profile_dataset() from ml-core/cleaning.py, which computes column statistics, outlier counts, correlations, class imbalance, and the 0–100 health score, and returns it all as JSON.

Django saves that JSON into Dataset.profiling_result and the overall score into Dataset.health_score, and flips status to 'profiled'. If FastAPI didn't respond (not running), none of this happens, but the upload itself still succeeded — the frontend is told profiling isn't done yet.

3. Diagnose page

React reads the dataset via datasetsAPI.get(datasetId) and renders the health score gauge, column cards, and correlation heatmap directly from profiling_result — no new computation needed, it was already stored in step 2.

4a. Smart Auto mode

React calls mlOpsAPI.autoPipeline(...) → FastAPI's /ml/auto → run_auto_pipeline() in ml-core/pipelines.py. This one function call auto-detects the task type, auto-cleans the data (auto_clean()), encodes categoricals, splits/scales, runs every recommended algorithm through run_tournament(), evaluates the winner, saves the model + scaler to disk, and returns everything — including an agent_decisions list that becomes the transparency log shown to the user.

4b. Guided Expert mode (the alternative path)

Instead of one big automatic call, React calls /ml/clean/step once per cleaning decision the user approves (run_cleaning_step() — fill one column, remove one set of outliers, etc.), then once the user is satisfied, calls /ml/train (run_full_pipeline()) with the specific algorithm they picked, or 'tournament' to compare several.

5. Results page

Whichever mode ran, the response includes metrics, feature_importance, and (for classification) the confusion matrix — all computed by evaluation.py's functions and already JSON-safe (no raw NaN or numpy types leak through, by design). React renders charts directly from this data; it never computes a metric itself.

6. What-If Simulator

Every time the user drags a slider, React calls mlOpsAPI.whatIfPredict(...) and whatIfContributions(...) → FastAPI loads the saved model + scaler from disk (predict_what_if(), get_feature_contributions()), scales the new input values using the exact same scaler fitted during training, and returns a prediction with confidence and per-feature contribution percentages. This must stay fast because it fires on every slider movement.

8 — Environment Variables and Secrets

Two separate .env files exist, one per backend, and neither is ever committed to git (both are listed in .gitignore, along with .venv/ and node_modules/):

FileContains
backend-django/.envDB_NAME, DB_USER, DB_PASSWORD, DB_HOST, DB_PORT — your real PostgreSQL credentials.
backend-fastapi/.envDEEPSEEK_API_KEY — the LLM key for future insight-card generation.

Each has a matching .env.example file committed to git instead, with the variable names but no real values — this is how a teammate (or you, on a new machine) knows what to fill in without ever seeing the real secret. load_dotenv() (from the python-dotenv package) reads the real .env file at startup and makes its values available via os.getenv("VAR_NAME").

If you ever see a real API key or password in a git diff
Stop and remove it before committing. A secret committed to git history is very difficult to fully erase later — every clone of the repo keeps a copy of every past commit.

11 — Things Worth Knowing: Beginner Pitfalls
  • numpy types are not JSON types. numpy.int64, numpy.bool_, and raw NaN all crash Python's json encoder even though they look like normal numbers. Every ml-core function that returns data explicitly casts to int()/float()/bool() for exactly this reason. If you add a new ML function later and it crashes with "Object of type X is not JSON serializable", this is almost always why.
  • The original file is never overwritten. Every cleaning function returns a brand-new DataFrame (df = df.copy() internally) instead of modifying in place. This is what makes DatasetVersion (original → cleaned → encoded → normalized) possible — if a function silently mutated the input, you could never get the original back.
  • Forgetting to run migrations after changing a model is the single most common Django error you'll hit. If a field you just added doesn't seem to exist, this is why — see Section 4.
  • Two venvs mean two installs. If you add a new package that Django's code needs (like requests was added for the FastAPI bridge), you must pip install it with Django's venv active, not FastAPI's, and vice versa for ML packages.
  • Port collisions. If Vite says "Port 5173 is in use, trying another one," something else (often a leftover dev server from an earlier session) is still running. Either use whatever port it lands on, or find and stop the old process first.
  • 0.0.0.0 vs localhost. Uvicorn prints http://0.0.0.0:8001 in the terminal — that address means "listen on every network interface," it is not a real page to visit. Always open http://localhost:8001 in your browser instead.
  • The graceful-degradation pattern is everywhere on purpose. Django's upload view catches FastAPI being offline; FastAPI's endpoints catch bad file paths and unknown algorithm names. A crash in one operation should never take down an entire server — it should return a clear error and let everything else keep working.
  • CORS errors show up in the browser console, not the server logs. If React's network tab shows a request that never got a response, or the console says "blocked by CORS policy," check that the exact origin React is running on (including the port) is in both backends' allowed-origins lists.
