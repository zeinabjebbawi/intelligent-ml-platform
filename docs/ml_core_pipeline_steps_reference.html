IntelliML — Cleaning Pipeline Steps: Complete Reference

Detailed explanation of all 10 steps in the execution diagram — what each function does, why it exists, and what flows between steps

01
User uploads CSV file
Django endpoint — file storage — FastAPI triggered

The pipeline starts when a user uploads a CSV file through the React frontend. React sends the file as a multipart form POST request to Django at /api/projects/<uuid>/datasets/upload/. Django saves the file to disk at media/datasets/user_{id}/project_{id}/original.csv and creates a Dataset record in PostgreSQL with the file path. Django then calls FastAPI asynchronously to begin the analysis pipeline.

Why this way? Django handles file storage and database records. FastAPI handles the heavy computation. This separation means the file is safely stored before any ML processing begins — if FastAPI crashes mid-analysis, the original file is never lost.

multipart/form-data
key: "file"
value: CSV file bytes
Django responds
{ dataset_id: "uuid",
  filename: "...",
  storage_path: "..." }
02
cleaning.load_data( filepath )
returns: raw pandas DataFrame

The pipeline's first Python call. FastAPI receives the file path from Django and calls load_data(filepath). This uses pd.read_csv(filepath) to read the CSV from disk into a pandas DataFrame. The DataFrame holds the data in memory as a table of rows and columns — exactly as uploaded, completely untouched.

Why not read the file directly in FastAPI? Centralizing file loading in load_data() means every part of the system loads CSVs the same way. If you later change from CSV to Parquet or add encoding detection, you change one function, not ten places in the code.

filepath: string
e.g. "media/datasets/

 original.csv"
Returns
raw_df: pandas DataFrame
→ every row and column
→ no modifications made
→ includes NaN values
03
cleaning.profile_dataset( df, target_column )
returns: profiling_result dict with health score, metadata, outliers, correlations

The most important single function call in the entire pipeline. It receives the raw DataFrame and calls five helper functions internally, in this exact order:

  • get_column_metadata(df) — for every column: type (numerical/categorical), missing count and percentage, mean/median/std/min/max for numbers, most-common value for text
  • count_outliers_per_column(df) — counts outliers in every numerical column using IQR method
  • compute_correlations(df) — Pearson correlation between every pair of numerical columns (for the heatmap)
  • detect_class_imbalance(df, target_column) — checks if the target column is heavily skewed toward one class. [Only runs if target_column is provided]
  • compute_health_score(profiling_result) — computes a 0 — 100 score from four sub-scores: completeness (40%), duplicates (20%), outliers (20%), balance (20%)

The assembled result is stored in Dataset.profiling_result as a JSONB column in PostgreSQL. This is what React reads to render the Diagnose page: health score gauge, column passports, correlation heatmap, and AI insight cards.

This step always runs immediately after upload. It is not optional and is not deferred. The user should see their dataset diagnosed before they do anything else.
Receives
df: raw DataFrame
target_column: string
  or None
Returns
profiling_result: {
 total_rows, total_columns,
 missing_pct_overall,
 duplicate_rows,
 outlier_counts,
 columns_metadata,
 correlations,
 class_imbalance,
 health_score: {overall,
  completeness, duplicates,
  outliers, balance}
}
04
cleaning.build_auto_clean_config( profiling_result )
returns: config dict — decisions only, no data modified

This is a pure decision function. It reads the profiling result and applies rules to decide which cleaning steps are needed. Critically, no DataFrame is involved here at all. The function only reads numbers from the profiling dict and writes decisions into a config dict. No data is modified in this step.

The decision rules it applies:

  • If duplicate_rows > 0 — set remove_duplicates: True
  • For each numerical column: run check_normality(df, col) — if normal, set method to "zscore"; if not normal (skewed), set method to "iqr" — IQR is more robust for non-normal data
  • If outlier density exceeds 2% — set remove_outlier_method per column
  • If any column has >90% missing values — add it to columns_to_drop (it is useless)
  • Set fill_numerical_strategy to "mean" or "median" based on outlier density in each column
In Smart Auto mode: this config is fed directly to auto_clean(). In Expert mode: this config is displayed to the user as recommendations. The user then decides what to apply.
Receives
profiling_result: dict
(from Step 3)
Returns
config: {
 remove_duplicates: bool,
 fill_numerical_strategy: str,
 fill_categorical_strategy: str,
 remove_outlier_method: str,
 columns_to_drop: list
}
05
cleaning.auto_clean( df, profiling_result, target_col )
returns: (cleaned_df, summary_list) — 5 internal sub-steps in sequence

This is where the actual data transformation happens. It calls build_auto_clean_config() internally and then executes the approved operations in a strict sequence. Each step is conditional — it only runs if the config says it should. The order is deliberate and important:

  • Step 1: drop_columns() — drops columns with >90% missing values. [conditional] Must run FIRST so later steps don't try to fill values in useless columns
  • Step 2: remove_duplicates() — removes exact duplicate rows. [conditional] Must run before filling missing values, or duplicates might be filled inconsistently
  • Step 3: fill_missing_with_mean/median() — fills NaN in every numerical column using the strategy decided in config (mean if low outliers, median if high outliers). Runs for every numerical column with any NaN values
  • Step 4: fill_missing_categorical() — fills NaN in every text/categorical column with mode (most common value)
  • Step 5: remove_outliers_iqr() or remove_outliers_zscore() — removes outlier rows from numerical columns (except the target column, which is never touched). [conditional: only if outlier density exceeds 2%] Runs last because outlier removal reduces the number of rows — we want to do this after filling missing values, not before

The function returns two things: the cleaned DataFrame (saved as cleaned_v2.csv) and a human-readable summary list that becomes the transparent activity log shown to the user.

Original file is never touched. The function starts with df = df.copy() in every atomic function it calls. original.csv on disk is never modified.
Receives
df: raw DataFrame
profiling_result: dict
target_column: string or None
Returns
cleaned_df: DataFrame
 (new, not the original)
summary: [
 "Removed 3 duplicates",
 "Filled 12 missing in Age",
 "Removed 4 outliers in BMI",
 ...]
06
cleaning.encode_categorical_columns( cleaned_df )
conditional — returns: (encoded_df, encoding_map)

ML algorithms only understand numbers. If the dataset has text columns like Gender ("Male","Female") or City ("Beirut","London"), they must be converted to integers before training. This function applies LabelEncoder from scikit-learn to every text/categorical column.

The encoding_map returned is crucial for transparency. It records exactly what was converted to what: {"Gender": {"Female": 0, "Male": 1}}. This map is stored in DatasetVersion.transformations_applied so the user can see "Male was mapped to 1, Female to 0" in the activity log.

The target column is excluded from encoding. If we encode "Diabetic/Not Diabetic" before the split, it becomes 0/1, which is fine. But we need to be careful that the target column labels remain interpretable for the evaluation output. Pass exclude_columns=[target_column] to preserve it unless it's already numerical.

This step is conditional — it only runs if the cleaned DataFrame still has categorical (text) columns after cleaning. If all columns are already numerical, this step is skipped entirely.

Receives
cleaned_df: DataFrame
exclude_columns: list
 (e.g. [target_column])
Returns
encoded_df: DataFrame
 (text → integers)
encoding_map: {
 "Gender": {"Male":1,"Female":0},
 "City": {"Beirut":0,"London":1}
}
07
pipelines.split_features_target( df, target_column )
returns: X (all features) and y (target Series)

Before training, the data must be split into two parts: X (the input features — everything the model learns from) and y (the target — what the model is trying to predict). This function simply removes the target column from the DataFrame to produce X, and returns the target column alone as y.

Why must the target be separated? If the target column stays in X, the model will accidentally learn to predict by reading the answer directly. This is called target leakage and produces a model with 100% accuracy on training data that completely fails in the real world. Separating them at this step prevents this from happening.
Receives
df: encoded DataFrame
target_column: string
 (e.g. "Outcome")
Returns
X: DataFrame
 (all columns except target)
y: pandas Series
 (the target column alone)
08
pipelines.split_train_test( X, y, test_size=0.4 )
returns: X_train, X_test, y_train, y_test (4 arrays)

The dataset must be split into two independent groups: a training set (what the model learns from) and a test set (what we use to measure its real performance on unseen data). We use 40% for testing (test_size=0.4), meaning 60% trains the model.

Why 60/40 instead of 80/20? The course used 60/40 which is a valid choice. A larger test set gives a more reliable estimate of real-world performance but leaves less data for training. For most educational datasets (hundreds to thousands of rows), 60/40 works well.
What is stratify=y? For classification tasks, we pass stratify=y so that both the training and test sets have the same class proportions as the original. Without it, you might get a training set that's 95% class 0 and a test set that's 60% class 1 — making the evaluation meaningless.

The split is deterministic: we always pass random_state=42, meaning the same data will always produce the same split. This guarantees reproducibility — running the same experiment twice produces identical results.

Receives
X: features DataFrame
y: target Series
test_size: 0.4 (default)
random_state: 42
Returns
X_train: 60% of X rows
X_test: 40% of X rows
y_train: matching 60% of y
y_test: matching 40% of y
09
pipelines.scale_features( X_train, X_test )
fits scaler on X_train ONLY — returns: X_train_scaled, X_test_scaled, scaler

StandardScaler normalizes each feature so that it has a mean of 0 and a standard deviation of 1. Without this, a feature like "Age" (values 18-90) would dominate a feature like "Glucose" (values 40-200) purely because its numbers are larger, not because it's more important. Scaling puts every feature on an equal footing.

The most important ML rule in this entire pipeline: the scaler FITS only on X_train. It learns the mean and standard deviation from the training data only. It then TRANSFORMS both X_train and X_test using those same learned values. Never fit the scaler on all data before splitting. If you do, the test set's statistics influence the scaler, which means the model indirectly "sees" the test set during training. This is called data leakage and inflates accuracy scores.

The scaler object itself is returned and saved to disk alongside the trained model. This is essential for the What-If Simulator: when a user inputs slider values (e.g., Glucose=180), those values must be scaled using the exact same mean and std that were used during training, otherwise the prediction will be wrong.

Receives
X_train: 60% split features
X_test: 40% split features
Returns
X_train_scaled: normalized
X_test_scaled: normalized
 (same scaler applied)
scaler: fitted StandardScaler
 (saved for What-If Simulator)
10
→ models.py receives the prepared data
pipelines.py hands off: X_train_scaled, X_test_scaled, y_train, y_test

At this point the cleaning pipeline is complete. pipelines.py passes four arrays to models.py: X_train_scaled, X_test_scaled, y_train, y_test. The data is clean, encoded, split, and normalized — ready for any algorithm.

models.py then does one of two things depending on the mode. In Auto mode, it calls run_tournament() with all recommended algorithms and returns a leaderboard. In Expert mode, it calls the specific train_*() function the user selected.

The final outputs of the training step (the fitted model and scaler) are saved to disk by save_model(). The experiment record in PostgreSQL stores the metrics as a JSONB column. evaluation.py reads the fitted model and the test data to compute all metrics, feature importance, and eventually power the What-If Simulator.

What flows back to the user? A complete results dict containing: accuracy (or RMSE/R² for regression), confusion matrix, feature importance, the health score that was computed in Step 3, the cleaning summary from Step 5, and the full insight cards generated by DeepSeek reading all of the above.
